# PR10 — Circuito operativo de gestión del club

## Objetivo

Completar el flujo que convierte una solicitud pública en un socio activo con programa asignado, asistencia verificable y seguimiento de actividad.

```text
Visitante
  └─ /join: solicitud + consentimiento
       ├─ Persistencia en membership_applications
       └─ Aviso al club y acuse de recibo por correo
            └─ /admin/user: revisión y creación de cuenta
                 └─ Alta de programa, entrenador y matrícula
                      └─ /coach/sessions: sesión y QR rotativo
                           ├─ Alumno: check-in QR validado
                           └─ Coach: asistencia manual
                                └─ Dashboard: XP, misiones, insignias y actividad
```

## Cambios implementados

### Admisiones y administración

- `POST /api/center-activity` guarda cada solicitud válida usando el mismo `Idempotency-Key` que el envío de correo.
- Se añade `membership_applications`, con datos de contacto, consentimiento, estado de revisión, notas internas y auditoría de quién revisó la solicitud.
- El panel `/admin/user` permite:
  - revisar y actualizar el estado de solicitudes;
  - crear/invitar cuentas;
  - crear programas;
  - asignar entrenadores;
  - matricular alumnos en programas.

La solicitud y el correo siguen siendo operaciones separadas: si el proveedor de correo falla, la solicitud permanece registrada para su seguimiento.

### Asistencia y QR

- `/coach/attendance` deja de reutilizar el check-in del alumno y pasa a mostrar alumnos activos por sesión para que el coach pueda marcarlos manualmente.
- La marca manual valida autenticación, rol, titularidad del programa y matrícula activa antes de crear el registro.
- Los alumnos ya no pueden insertar asistencia directamente con la API de Supabase: deben pasar por `check_in_attendance`, que comprueba sesión, QR, vigencia, horario y matrícula.
- El QR se genera localmente con `react-qr-code`; no se envía el token a servicios externos.
- La pantalla QR incorpora la rotación del token y las sesiones creadas desde el panel caducan al terminar su horario.

### Actividad y progreso

- Registrar un entrenamiento muestra el valor que realmente calcula el sistema: `+10 XP`.
- Un trigger concede las insignias de primer entrenamiento y primera asistencia.
- Los alumnos reciben las misiones activas y sus progresos se recalculan al registrar entrenamiento o asistencia.
- El dashboard muestra próximas sesiones y las últimas asistencias, además de los elementos existentes de XP, racha, misiones, insignias y clasificación.

## Migración

La implementación requiere aplicar:

```text
supabase/migrations/20260904110000_complete_club_operations.sql
supabase/migrations/20260904120000_enforce_program_roles.sql
```

Incluyen la tabla de solicitudes, sus permisos RLS, el cierre de la inserción directa de asistencia y los triggers de progreso. La segunda migración exige además que responsables de programa y asignaciones tengan rol `coach` o `admin`, y que las matrículas pertenezcan a perfiles `student`.

Las migraciones se aplicaron y verificaron en producción. Para futuros despliegues:

```bash
supabase db push
```

La configuración Auth declara `https://cejoventut.com` como `site_url`, de modo que los correos de invitación muestran el dominio público. Tras fusionar este cambio debe sincronizarse también con Supabase mediante `supabase config push` usando un token con permiso `auth_config_write`.

### Pruebas E2E

El comando `npm run test:e2e` solo acepta `.env.test.local`, que debe apuntar a un proyecto Supabase de pruebas separado. No carga `.env` ni utiliza las credenciales de producción. Antes de ejecutarlo, copiar `.env.test.example` y configurar el proyecto y las cuentas de prueba.

El script asigna automáticamente:

```text
ADMIN      <- ADMIN2
ADMIN_PASS <- ADMIN_PASS2
COACH      <- COACH2
COACH_PASS <- COACH_PASS2
```

El mapeo se implementa en `scripts/test-e2e.mjs`; también lo utiliza `npm run test:e2e:ui`. El archivo exige `E2E_TEST_ENV=1` y las credenciales `ADMIN2`, `ADMIN_PASS2`, `COACH2`, `COACH_PASS2`, `STUDENT` y `STUDENT_PASS`.

Última ejecución:

```bash
npm run test:e2e
```

Resultado: 9 de 9 pruebas Playwright correctas contra el proyecto dedicado configurado en `.env.test.local`, incluidas autenticación por rol, acceso QR/asistencia y formularios públicos.

La comprobación visual del servidor de desarrollo confirmó que la página de inicio carga contenido, muestra los elementos principales y no presenta un overlay de errores de Next.js.

## Pendiente de decisión funcional

El rol `parent` se conserva por compatibilidad, pero no existe todavía un modelo tutor-menor ni permisos familiares. Antes de habilitarlo hay que definir relaciones familiares, consentimiento, visibilidad de asistencia y responsabilidades de pago.
