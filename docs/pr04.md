## Resumen ejecutivo

El repositorio compila, pasa ESLint, dispone de una base de datos reproducible y se ha completado el plan de endurecimiento prioritario. Las operaciones de sesiones y QR ya no usan `service_role`, la administración comprueba el rol en servidor y las migraciones validadas están aplicadas en el proyecto remoto. El recorrido administrador → coach → programa → sesión → alumno → matrícula → check-in también se verificó con datos operativos.

No se copiaron datos personales. Permanecen mejoras secundarias recomendables —protección antiabuso de formularios públicos, reducción de mensajes internos y ampliación de pruebas end-to-end—, pero los hallazgos críticos de autorización descritos en la revisión inicial quedaron corregidos.

## Base de datos reconstruida

La inspección inicial del proyecto remoto confirmó que su esquema `public` solo contenía `news_articles`. Las tablas de perfiles, programas, asistencia y gamificación referenciadas por la aplicación no existían allí, por lo que no era posible obtenerlas mediante un volcado completo.

Se reconstruyó el esquema a partir de las consultas, relaciones y RPC utilizadas por el código:

- 12 tablas públicas: `profiles`, `programs`, `coach_programs`, `enrollments`, `attendance_sessions`, `attendance_logs`, `training_logs`, `badges`, `user_badges`, `quests`, `user_quests` y `news_articles`;
- relaciones, claves foráneas, índices, restricciones y timestamps;
- 23 políticas RLS sobre las tablas de la aplicación;
- funciones auxiliares para comprobar administradores, entrenadores y matrículas;
- las RPC `xp_summary_for_user`, `current_streak_days`, `leaderboard_top`, `upcoming_sessions_for_user`, `check_in_attendance` y `coach_session_qr`;
- una vista de compatibilidad `attendance` sobre `attendance_logs`;
- semillas sin información personal: tres insignias y dos misiones.

Archivos añadidos:

- [`supabase/config.toml`](../supabase/config.toml), configuración de Supabase local;
- [`20260729190000_reconstruct_club_schema.sql`](../supabase/migrations/20260729190000_reconstruct_club_schema.sql), esquema reconstruido;
- [`supabase/seed.sql`](../supabase/seed.sql), datos de referencia;
- [`docs/database-local.md`](database-local.md), instrucciones para levantar y reiniciar la base.

La migración evita derivar roles desde metadatos enviados durante un registro público. Los perfiles y roles privilegiados se crean mediante un flujo administrativo autenticado. También impide modificar el campo `role` desde una cuenta normal y oculta las claves QR a los alumnos; el check-in se ejecuta mediante una RPC atómica.

Validaciones realizadas:

- dos recreaciones completas mediante `supabase db reset`;
- `supabase db lint --local --level warning`, sin errores;
- comprobación en catálogo de 12 tablas con RLS, 23 políticas y seis RPC;

- `npm test`: 3 pruebas de redirección y 14 pruebas pgTAP, todas correctas.
- `npm run test:e2e`: 6 pruebas Playwright en Chromium, todas correctas.

La instancia puede recrearse con:

```bash

```

El `dry-run` remoto mostró únicamente las dos migraciones esperadas. Ambas se aplicaron correctamente y una extracción posterior confirmó las políticas y seis RPC.

La URL y la anon key se leen ahora mediante referencias estáticas `NEXT_PUBLIC_*` y se exponen explícitamente desde `next.config.mjs`. El build confirmó que ambos valores están presentes; la `service_role` continúa siendo exclusivamente de servidor.

Esta comprobación valida conjuntamente Auth, perfiles, roles, ownership, matrícula, visibilidad de sesiones, protección de la clave QR y escritura de asistencia.

## Pruebas end-to-end

Se añadió Playwright con arranque automático de Next.js y ejecución secuencial en Chromium. Las credenciales se leen desde `.env` y nunca se incluyen en el código o los informes.

Escenarios cubiertos:

- un visitante anónimo es redirigido al login al intentar abrir administración;
- el administrador puede acceder a la creación de usuarios;
- el coach puede gestionar sesiones y no puede acceder a administración;
- el alumno puede abrir su dashboard y no puede acceder al panel del coach;
- el coach puede abrir el QR de una sesión asignada;
- el alumno vuelve al enlace de asistencia después del login y una clave QR inválida es rechazada.

La prueba del QR usa una clave deliberadamente inválida y no crea asistencias ni modifica datos de producción. En caso de fallo, Playwright conserva captura, vídeo y traza en directorios ignorados por Git.

Última ejecución verificada el 30 de julio de 2026:

- `npm run test:e2e`: 6/6 pruebas superadas en Chromium;
- `npm run test:e2e:ui`: Playwright UI iniciado correctamente y disponible para ejecución interactiva.

Comandos:

```bash
npm run test:e2e
npm run test:e2e:ui
```

`npm test` ejecuta también pgTAP y requiere Docker Desktop activo; el script
arranca Supabase local automáticamente cuando el daemon está disponible.

## Hallazgos críticos

1. Creación de usuarios y administradores sin autorización

Estado: **resuelto**.

La acción [`createUserAdmin`](../app/admin/user/actions.ts:14) usa `service_role` y permite elegir el rol, incluido `admin`, sin comprobar sesión ni rol del solicitante.

La página está en `/admin/user`, pero la protección se colocó erróneamente en [`app/api/admin/layout.tsx`](../app/api/admin/layout.tsx:5). Ese layout solo afecta a `/api/admin/*`, no a `/admin/*`.

Impacto: un visitante podría invocar la Server Action y crear cuentas privilegiadas.

Solución: crear `app/admin/layout.tsx`, validar la identidad con `auth.getUser()` y volver a verificar `profiles.role === "admin"` dentro de la propia acción. La protección visual del layout no sustituye la autorización en servidor.

Se añadió el layout correcto y la acción vuelve a comprobar usuario y rol antes de crear cuentas.

2. Creación arbitraria de sesiones con `service_role`

Estado: **resuelto**.

Estas rutas usan la clave administrativa sin autenticar ni verificar que el usuario controle el programa:

- [`POST /api/coach/sessions`](../app/api/coach/sessions/route.ts:19)
- [`POST /api/coach/attendance/create`](../app/api/coach/attendance/create/route.ts:6)

Aunque la acción legítima envía un Bearer token, la primera ruta nunca lo lee. Cualquier cliente puede crear sesiones para cualquier `program_id`.

Ambas rutas validan ahora usuario, rol y ownership del programa, y escriben con el cliente del usuario bajo RLS.

3. Rotación arbitraria de claves QR

Estado: **resuelto**.

[`PUT /api/coach/attendance/rotate`](../app/api/coach/attendance/rotate/route.ts:5) actualiza cualquier sesión mediante `service_role`, sin autenticación ni ownership.

Además, genera la clave con `Math.random()` en la [línea 18](../app/api/coach/attendance/rotate/route.ts:18), que no es apropiado para secretos.

Impacto: invalidación de códigos legítimos, interrupción de asistencia y manipulación de sesiones.

La rotación exige ownership, escribe bajo RLS y genera claves con `crypto.randomBytes`.

4. Posible fuga de tokens mediante Host header

Estado: **resuelto**.

[`getOrigin()`](../app/coach/sessions/actions.ts:9) construye un destino usando `x-forwarded-host`/`host`. Después, la acción hace una petición a ese origen incluyendo el access token del usuario en [`Authorization`](../app/coach/sessions/actions.ts:31).

Si la infraestructura permite influir en esos encabezados, el token puede enviarse a otro host. Es preferible no hacer HTTP interno: extraer la lógica a una función de servidor compartida. Como mínimo, usar un origen fijo y validado.

Las Server Actions operan ahora directamente con Supabase y no realizan peticiones HTTP internas.

## Hallazgos altos

5. El contrato de check-in está roto

Estado: **resuelto**.

La API responde:

```json
{ "status": "ok" }
```

en [`attendance/checkin/route.ts`](../app/api/coach/attendance/checkin/route.ts:107), pero la página comprueba `j.ok` en [`attend/page.tsx`](../app/attend/page.tsx:37).

Resultado: la asistencia puede registrarse correctamente y aun así mostrarse como error.

La API y la interfaz comparten ahora `{ ok, status, xp, duplicate }`; la operación es atómica e idempotente en PostgreSQL.

6. La vuelta al QR después del login no funciona

Estado: **resuelto**.

La página de asistencia enlaza a `login?redirectTo=...` en [`attend/page.tsx`](../app/attend/page.tsx:59), mientras el login solo lee el parámetro `next` en [`login/page.tsx`](../app/login/page.tsx:10).

Además, `next` se utiliza directamente en `router.replace(next)`, lo que debería restringirse a rutas internas para evitar redirecciones abiertas.

El login admite los nombres utilizados históricamente y solo acepta rutas internas validadas.

7. Superficies de depuración desplegadas

Estado: **resuelto**.

El build publica:

- [`/debug/session-client`](../app/debug/session-client/page.tsx:7)
- [`/debug/session-server`](../app/debug/session-server/page.tsx:7)

Ambas muestran información completa de sesión; la versión cliente serializa incluso los tokens disponibles para el navegador. Deben eliminarse o limitarse estrictamente a desarrollo.

Las dos rutas se eliminaron y ya no aparecen en el build.

8. Middleware desactivado

Estado: **resuelto**.

El archivo se llama [`middleware.off.ts`](../middleware.off.ts:1), por lo que Next.js no lo ejecuta. En consecuencia, tampoco se refrescan las cookies de Supabase desde middleware.

La autorización sensible debe mantenerse en cada endpoint incluso si se reactiva, pero la ausencia del middleware puede provocar sesiones caducadas o comportamiento inconsistente.

Se sustituyó por `proxy.ts`, el mecanismo de Next 16, que valida/refresca la sesión con `auth.getUser()`.

9. Confianza excesiva en `getSession()`

Estado: **resuelto en las decisiones de acceso del servidor**.

Varias rutas y layouts confían en datos locales de sesión:

- [`coach/layout.tsx`](../app/coach/layout.tsx:30)
- [`dashboard/page.tsx`](../app/dashboard/page.tsx:46)
- [`attendance/mark`](../app/api/coach/attendance/mark/route.ts:7)
- endpoints de alumnos de programas.

Para decisiones de autorización debe preferirse `auth.getUser()`, que valida el JWT con Supabase.

Layouts y endpoints protegidos usan ahora `getUser()`. El uso cliente de `getSession()` se conserva únicamente para obtener el token que acompaña peticiones autenticadas.

## Calidad y mantenibilidad

10. Base de datos reconstruida, pendiente de contrastar con el dominio

Estado: **reconstruida, probada y publicada**.

Este punto quedó resuelto técnicamente mediante la nueva migración reproducible. No obstante, el esquema se infirió del código porque el remoto solo contenía `news_articles`.

Antes de publicarlo deben revisarse con responsables del club las reglas funcionales asumidas: valores de XP, definición de rachas, estados de matrícula, duración de sesiones, permisos de entrenadores y contenido de misiones.

11. Inconsistencias de esquema

La eliminación de sesiones borra de `attendance` en [`sessions/[id]/route.ts`](../app/api/coach/sessions/%5Bid%5D/route.ts:64), mientras el resto del proyecto usa `attendance_logs`. Otra ruta aparentemente destinada a “rotate” implementa `DELETE` y elimina la sesión completa en [`qr/rotate/route.ts`](../app/api/coach/sessions/%5Bid%5D/qr/rotate/route.ts:6).

Son señales de endpoints duplicados o migraciones parciales.

12. Formularios públicos sin defensa de servidor

`/api/center-activity` puede enviar correo sin rate limiting, CAPTCHA ni control antiabuso. También interpola datos del usuario directamente en HTML en [`center-activity/route.ts`](../app/api/center-activity/route.ts:24), permitiendo inyección de HTML dentro del correo.

El formulario real usa EmailJS desde el navegador, mientras este endpoint queda como una segunda implementación. Conviene escoger una única arquitectura y protegerla en servidor.

13. Errores internos expuestos

Varias rutas devuelven directamente `error.message` de Supabase o excepciones. Eso facilita enumerar tablas, restricciones y detalles del backend. Deberían responder códigos estables y registrar el detalle solo en servidor.

14. Cobertura de pruebas inexistente

Estado: **resuelto con cobertura inicial**.

El repositorio dispone ahora de:

- 3 pruebas unitarias para redirecciones internas seguras;
- 14 pruebas pgTAP para esquema, RLS, roles, QR e idempotencia del check-in;
- 6 pruebas Playwright para autenticación, autorización por roles, panel del coach y retorno al QR.

Quedan como ampliación futura la creación/rotación/borrado de sesiones desde navegador, la sincronización RSS y la detección de idioma.

15. Rendimiento de imágenes

Estado: **resuelto para los activos utilizados**.

`public/` ocupa aproximadamente 19 MB y [`her.jpg`](../public/her.jpg) pesa alrededor de 7,9 MB. Además, `images.unoptimized: true` en [`next.config.mjs`](../next.config.mjs:7) desactiva la optimización de Next.

Esto perjudica especialmente LCP y navegación móvil.

La portada y las tres imágenes reales de galería se sirven como WebP: pasan de aproximadamente 4,5 MB a 208 KB en total. Next vuelve a optimizar imágenes en AVIF/WebP según el navegador. Los originales se conservaron.

16. Sitemap desalineado con las rutas

Estado: **resuelto**.

[`sitemap.ts`](../app/sitemap.ts:9) publica `/competition-results` y `/contact`, pero esas rutas no aparecen en el build. Esto genera URLs indexables con 404.

Las dos rutas inexistentes se eliminaron del sitemap.
