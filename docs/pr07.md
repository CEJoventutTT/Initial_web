# PR07 — Consolidación de altas y entrega de correos

## Objetivo

Consolidar el alta administrativa de usuarios y hacer trazable la entrega de
correo de contacto e inscripción. El resultado debe evitar duplicados en los
casos recuperables, permitir reenvíos intencionados y no dejar cuentas Auth
inconsistentes sin una compensación o una vía de reconciliación.

## Implementación realizada

### Alta administrativa

- `/admin/user` es el único punto de entrada de altas: la ruta paralela
  `POST /api/admin/users` se ha retirado.
- La acción mantiene la comprobación de sesión y rol `admin`, y ahora valida
  formato de correo y rol antes de usar el cliente de servicio.
- Se conserva la invitación de Supabase como vía normal. Si falla, se crea la
  cuenta y se genera un enlace de recuperación con el mismo `redirectTo`.
- El enlace se muestra únicamente en la respuesta del panel administrativo,
  marcado como secreto de un solo uso. No se añade a los logs de la aplicación.
- Si falla la generación del enlace o la escritura del perfil, se intenta borrar
  la cuenta Auth creada. Si la compensación también falla, se deja un error con
  `user_id` para conciliación manual.

### Idempotencia y outbox

- Los formularios de contacto e inscripción generan un `Idempotency-Key` con
  `crypto.randomUUID()` al iniciar el formulario y lo reutilizan tras un error.
  Al completarse el envío se crea una clave nueva para el siguiente formulario.
- Las rutas rechazan solicitudes sin una clave válida de 16 a 128 caracteres.
  Los límites de frecuencia existentes por IP siguen aplicándose antes de crear
  la solicitud.
- Se añadieron `email_requests` y `email_deliveries`. Cada solicitud crea dos
  entregas independientes: `notice` y `acknowledgement`.
- Cada entrega conserva estado, proveedor, identificador, número de intentos,
  error, próximo intento y clave de idempotencia propia. La clave de Resend es
  estable por entrega; el fallback a EmailJS se ejecuta para esa entrega, no
  para la pareja de correos.
- El worker reclama entregas pendientes de forma atómica. Si el aviso ya se
  confirma y falla el acuse, solo se reintenta el acuse. EmailJS no proporciona
  una garantía equivalente de idempotencia frente a timeouts ambiguos.
- Las reclamaciones tienen un lease de quince minutos: una entrega que queda en
  `sending` tras interrumpirse el proceso vuelve a ser recuperable. El sistema
  conserva semántica al menos una vez frente a un resultado ambiguo del proveedor.
- Las filas pendientes, fallidas o en envío de la anterior `email_outbox` se
  migran como entregas pendientes para no abandonar correos en tránsito.
- Si solo una parte de una solicitud está entregada, las rutas devuelven `202`
  con `pending: true`; no comunican un `200` como si ambos correos estuvieran
  confirmados.

### Migraciones y pruebas

- Se añadieron estas migraciones, en este orden:
  - `20260902100000_split_email_outbox_deliveries.sql`: crea la solicitud y las
    entregas independientes.
  - `20260902103000_fix_email_delivery_claim_ambiguity.sql`: corrige la
    ambigüedad de la restricción de unicidad al reclamar entregas.
  - `20260902104000_return_claimed_email_deliveries_only.sql`: hace que el RPC
    devuelva únicamente las entregas reclamadas y no las que ya estaban en curso.
  - `20260902105000_recover_email_leases_and_legacy_outbox.sql`: recupera
    leases caducados y migra el trabajo recuperable de la outbox anterior.
- Las pruebas Jest cubren la petición idempotente, la entrega separada y el
  caso en que se confirma el aviso pero falla el acuse.
- Las pruebas pgTAP verifican el esquema, los RPC y el aislamiento de
  `email_deliveries` para usuarios autenticados.

## Verificación realizada

`supabase migration up --local`.
